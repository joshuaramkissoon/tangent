Cache the public API at the edge

The /v1/papers endpoints spend most of their time recomputing answers they gave a minute ago. This plan moves that work onto the CDN instead of scaling the database.

~400msp95 today, mostly the database
80%of requests repeat within a minute
0%cached now: every response says no-store

Approach

  1. Send Cache-Control: public, s-maxage=60, stale-while-revalidate=300 on read endpoints.
  2. Normalise the cache key: sort query params and drop tracking params like utm_*.
  3. Tag each response with surrogate keys (paper:123) so a write purges only what it touched.
  4. Turn on request coalescing so a cold key sends one request to the origin, not hundreds.

Risks

Thundering herd. When a popular key expires, every reader misses at once. Coalescing plus stale-while-revalidate means one refresh, served stale meanwhile.
Personalised responses leaking. Anything that reads the session cookie gets private, no-store, so one reader's page never reaches another.
Purge lag. Surrogate-key purges take ~150ms to propagate, so a reader may briefly see the old note right after saving.

Rollout

Ship behind a flag on /v1/search first, watch hit ratio and origin load for a day, then turn on the rest.
